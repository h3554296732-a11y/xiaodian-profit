# 小店利润本：产品范围与分阶段计划

> 已归档：本文保留早期设计、部署或验收记录，文中状态仅对应记录日期。当前功能和使用方法以 [README](../README.md) 与仓库代码为准；新环境的服务配置、价格和可用性请重新核对。

设计日期：2026-10-15。当前交付范围：需求分析、Windows 环境检查、Next.js / Tailwind 基础页面。

## 1. 解决什么问题

帮助校园小卖部、便利店、零食店等小商户回答三个问题：这段时间卖了多少钱、扣除已知成本后大约赚了多少、哪些商品贡献了更多毛利。

首页先给经营结果，录入入口保持明显。界面以中文、人民币和手机操作为主，同时适配 Windows 浏览器。避免把专业会计科目、复杂审批或员工权限带入第一版。

## 2. 第一版的默认约定

| 事项 | MVP 约定 |
| --- | --- |
| 商户与账号 | 一个已注册账号管理一家店；暂不支持员工、门店切换或店铺转让 |
| 货币 | 人民币 CNY；界面显示两位小数；数据按整数“分”存储和计算 |
| 时间 | 经营日期采用 Asia/Shanghai；一周从周一开始 |
| 数量 | 按件记数，只允许正整数；称重商品、退货与赊账暂不支持 |
| 成本口径 | 每次销售保存当时确认的单位成本；当前商品成本只是新记录的默认值 |
| 费用口径 | 在商户选择的发生日期计入已记录费用；MVP 不自动摊销租金等月度费用 |
| 库存 | 不承诺进销存、库存数量、库存金额、加权平均成本或先进先出核算 |
| 其他收入 | 配送费等订单级收入记在销售单头，一张单只计入一次 |
| 结果名称 | 一律使用“估算经营利润”，并说明可能尚未包含税费、人工及其他必要成本 |

上述约定用于先做成一个可验证的产品。涉及真实经营模式变化时，先调整规则和测试，再扩展功能。

## 3. 核心功能与使用流程

| 功能 | 最小可用行为 | 验收重点 |
| --- | --- | --- |
| 商品管理 | 新增、编辑、搜索商品；记录名称、类别、进货单价、销售单价；删除表现为停用 | 单件毛利和毛利率正确；停用商品不再供新销售选择，历史记录仍可阅读 |
| 销售记录 | 选择商品、填数量、确认本次实际售价与单位成本；可加入多件商品和订单额外收入 | 保存历史快照；可查看、纠正历史销售；更改商品现价不会改写历史利润 |
| 经营费用 | 记录运输、包装、损耗、水电、租金、其他费用的日期、金额和备注 | 费用只计入一次；损耗与已售成本不能重复扣除 |
| 经营概览 | 展示今日营业额、今日估算利润、本周和本月利润、销量与毛利贡献榜、每日趋势 | 使用同一套计算规则；没有数据时给空状态；图表有金额和日期说明 |
| 账号与数据 | 使用 Supabase 注册、登录、保存记录 | 两个商户互相无法读取、修改或挂接对方的数据 |

每日录入的目标流程是“记录销售 → 选商品 → 填数量 → 确认金额 → 保存”。价格和单位成本默认带入，但允许商户按本次实际情况确认。历史编辑必须明确正在修改哪一天的记录。

## 4. 统一计算口径

设同一期间所有有效销售明细为 i：

```text
商品销售收入 = Σ(数量 i × 本次实际销售单价 i)
其他营业收入 = Σ(每张有效销售单的额外收入)
营业收入 = 商品销售收入 + 其他营业收入
商品销售成本 = Σ(数量 i × 本次确认的单位成本 i)
毛利润 = 营业收入 − 商品销售成本
估算经营利润 = 毛利润 − 同期已记录经营费用
估算利润率 = 估算经营利润 ÷ 营业收入 × 100%
商品单件毛利 = 销售单价 − 进货单价
商品毛利率 = 商品单件毛利 ÷ 销售单价 × 100%
```

营业收入或销售单价为 0 时，相应利润率显示“—”，不能显示无穷大。允许负利润。商品毛利贡献榜只统计商品销售收入减商品销售成本，不把订单配送费任意分摊给商品，因此榜单合计可能与整店毛利润不同。

算例：进货 100 瓶水，每瓶 2 元，今天售出 10 瓶，每瓶 3 元，另收配送费 2 元、发生包装费 1 元。营业收入 32 元，已售成本 20 元，毛利润 12 元，估算经营利润 11 元，利润率约 34.38%。这批进货的 200 元不能全部当作今天的已售成本；剩下 90 瓶仍是未售商品。由于 MVP 不管理库存，系统不会声称已计算出这些库存的实际账面价值。

损耗费用只能对应未售出且实际损耗商品的成本，避免已售商品成本再次作为损耗录入。每月一次录入的租金会集中影响该日利润，应在后续报表中清楚提示这种按发生日期记录的口径。

## 5. 技术方案

| 层次 | 选择及原因 |
| --- | --- |
| 前端与应用 | Next.js App Router + TypeScript：统一页面、路由和后续服务端逻辑，减少初学者维护多个服务的负担 |
| 样式 | Tailwind CSS：先建立统一颜色、间距、卡片、表单与移动端导航 |
| 数据与认证 | 后续接入 Supabase Auth + PostgreSQL；数据库层用 RLS 隔离店铺 |
| 金额计算 | 将输入的十进制金额字符串转换成整数分；计算与显示分开；后续由服务端重复校验 |
| 版本管理 | 本地 Git；确认代码可运行、密钥不入库后，再建立 GitHub 远程仓库 |
| 部署 | 后续选择支持 Next.js 的托管平台并连接 Supabase；上线前验证 HTTPS、认证回调、备份和访问权限 |

本地和后续部署运行时采用仍受依赖支持的 Node.js 版本。Supabase 已公告客户端不再支持 Node.js 20，接入阶段应使用 Node.js 22 或更高的受支持版本，具体版本以实际依赖和检查结果为准。[官方公告](https://supabase.com/changelog/45715-deprecation-notice-dropping-support-for-node-js-20)

## 6. 按阶段推进

| 阶段 | 对应原流程 | 交付与验收 | 主要风险 |
| --- | --- | --- | --- |
| A：方案与页面基础（本轮） | 1–3 | 产品与数据设计文档；环境检查；可启动的基础页面、导航、手机及桌面布局；明确所有示例数据 | 页面预览不等于业务可用；未连接数据库、未验证隔离策略 |
| B：商品管理 | 4 | 商品表单、编辑、搜索、停用及毛利显示；验证空名称、非法金额、零售价、负毛利 | 浏览器临时数据可能丢失，接入数据库前不得当正式账本 |
| C：销售、费用与计算 | 5 | 快速录入、历史纠正、价格成本快照、费用和统一计算模块 | 浮点误差、额外收入重复、商品改价污染历史、误把进货当已售成本 |
| D：真实账号与保存 | 6 | Supabase 注册/登录、持久化、RLS、复合外键、原子销售提交 | 越权访问、半张销售单、重试重复记账、并发覆盖 |
| E：经营看板 | 7 | 从真实有效记录计算期间指标、趋势和两个排行榜 | 时区边界错误、订单头与明细关联造成收入翻倍、空值误导 |
| F：完整验收 | 8（测试贯穿各阶段） | 金额测试、两账号权限测试、关键流程与移动端验收；故障修复后复测 | 测试通过不代表涵盖所有真实经营情况，应先做小范围试用 |
| G：部署与试运营 | 9 | GitHub、托管平台、环境变量、Supabase 回调和域名；实际公网注册与跨账号验证 | 邮件送达、服务费用、备份恢复、数据隐私与运营支持尚需准备 |

每阶段交付时报告：实际实现、运行过的验证、仍未验证的内容、下一阶段风险。不能把“文件已经写好”“命令没有报错”当作完整验收。

## 7. 本轮的边界与检查方式

本轮只实现基础页面。任何指标、图表或商品若用于展示，必须标记“示例数据”，并避免让用户误以为已保存账目。注册、保存、新增等尚未实现的动作应有明确的状态说明，不能给出虚假的成功提示。

本轮检查内容：Windows 中的 Node.js / npm / Git 可用性；项目安装与启动；TypeScript、代码检查和生产构建；常见手机宽度与桌面宽度的页面、导航、溢出和基本键盘操作。具体结果以开发交付记录为准，本文不预先宣称检查通过。

当前不创建 Supabase 项目、不提交数据库迁移、不实现真实增删改查或登录、不查询真实经营数据、不发布到互联网。后续开始商品管理，再沿用已确定的金额和历史数据规则。

## 8. 上线前必须补齐的事情

除了功能，需要真实注册邮件与找回密码、两商户隔离测试、输入限制、销售原子提交、重复请求保护、错误恢复、敏感信息管理和备份恢复演练。试运营前明确服务条款、隐私说明、商户数据导出与账号删除流程。涉及收费及面向特定地区正式经营时，再核实当时适用的合规要求。

AI 建议、支付、扫码收银、库存核算、多员工和复杂财务报表均留待真实用户反馈后评估。
